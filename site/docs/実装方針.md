# 実装方針

## 文書の位置付け

> **結論：本文書は，画面設計とbackendの公開仕様を，frontendの技術構成，モジュール分担，データ境界および検査手順へ具体化する．**

サービス範囲と事業要件は`business-research`，利用者体験とページ責務は[グランドデザイン](グランドデザイン.md)，表示・操作・文言は[画面設計](画面設計.md)，計算式と公開データは`backend`を正本とする．本文書では，これらの内容を変更せず，実装上の分担と手順だけを定める．文書体系全体は[frontend README](../../README.md#文書体系)を参照する．

## 基本方針

> **結論：MVPは，静的サイトとしてブラウザ内の計算と事前生成データで完結させる．**

サイト本体にはHTML，CSSおよびブラウザ実行時の依存ライブラリを持たないJavaScript ES Modulesを使用する．複数HTMLの成果物生成にはVite，本番配信にはGitHub Pagesを使用し，Cloudflare Workers互換設定は従来検証用に限定する．実行時のサーバー処理，データベースおよびクラウド関数は使用しない．

公開リポジトリには秘密情報，APIキー，非公開データおよび内部処理用データを置かない．未確定の計算式または未検証のデータから採算値を生成せず，得にならない結果もそのまま表示し，採算が良く見えるように前提を変更しない．

必要性が確定するまで，フレームワーク，サーバー，データベースおよび外部解析サービスを追加しない．

## URL設計

> **結論：現行の公開URLはガイドを`/guides/`，診断を`/simulator/`へ分け，旧URLの転送を維持する．**

| URL | 役割 |
|---|---|
| `/` | TOPの診断入力 |
| `/guides/` | ガイド一覧 |
| `/guides/solar-economics/`・`/guides/subsidies/`・`/guides/quotes-contractors/`・`/guides/disaster/` | 公開4記事 |
| `/simulator/` | 診断 |
| `/pages/calculation-method.html`・`/pages/policy.html` | 計算根拠・運営方針 |

旧`/solar/`と旧記事HTMLの扱いは[ガイドURLの移転互換](#ガイドurlの移転互換)を正本とする．ソースの`solar/`には使用中のJS・CSS・記事メタデータがあるため，旧URLという理由で削除しない．

将来領域の配置方針は，給湯・熱源`/hot-water/`，断熱・窓`/insulation/`，料金プラン`/energy-plans/`，住宅エネルギー総合診断`/diagnosis/`とする．これらは初期公開範囲外であり，現行のガイドURLを移動する指示ではない．太陽光領域を`/solar/`へ集約する旧案は，現行ガイドには適用しない．

## JavaScriptの分担

> **結論：画面制御，公開データ読込および採算計算を分離する．**

| ファイル | 役割 |
|---|---|
| `site/simulator/src/top.js` | トップの初期化，入力制御，利用可否の表示および診断画面への遷移 |
| `site/simulator/src/app.js` | 診断画面の初期化，条件変更，結果表示および各処理の接続 |
| `data/src/data-loader.js` | 公開データの取得と版の整合性確認 |
| `site/simulator/src/calculator.js` | backend仕様と一致するブラウザ採算計算 |
| `site/articles/src/article-data.js` | 詳細記事への採用値と出典の反映 |

都道府県選択肢は`data/input/public-data.json`から生成し，frontend内に同じ一覧を重複して保持しない．

## backend連携

> **結論：実行時データは`data/input/`，backendとの一致確認専用データは`qa/fixtures/`へ分離する．**

| ファイル | 用途 |
|---|---|
| `data/input/public-data.json` | ブラウザ計算に必要な公開データ |
| `data/input/metadata.json` | スキーマ版，データ版，生成日時および出典概要 |
| `qa/fixtures/calculation-cases.json` | frontend計算とbackend基準計算の一致確認 |

公開データとメタデータの`schema_version`および`data_version`が一致しない場合は，計算機能を有効にしない．秘密情報またはbackendの内部データへ直接接続しない．

時間別プロファイルの正規化・年間合計・直接自家消費の合計は，基準実装のPython 3.12に合わせて補償和を用いる．8760項目の単純加算による誤差を，出力の許容差や期待値の変更で隠さない．費用の税区分が未確定のガードは集約判定と設備別算定の両入口へ適用し，十進の費用境界は整数交差積等で保持する．

容量前処理`min_input_round_0_01`は，太陽光モジュールとPCSへ同じ入力容量を対応させる仮定のもと，モジュールだけ小数第3位を四捨五入し，未丸めPCSとの小さい値を用いる．共通算式で集約・設備別の両入口へ適用し，両方を丸めたり，実機の出力同一性を確認済みと扱ったりしない．

容量前処理`round_0_001`は十進四捨五入で0.001kW単位へ丸める．太陽光上限判定用の`solar_output_max_kw_preprocessing`（`none`又は`round_0_001`）は金額用の`capacity_preprocessing`から独立させ，省略時は従来の生入力で判定する．上限指定を伴う契約に限り使用し，下限・蓄電池容量条件へ転用しない．全成分対象外の先行判定と成分ごとの算式で共通の上限判定を使い，太陽光成分が除外されても独立した蓄電池成分を一律除外しない．正式な制度採用・固定データ同期は，計算機能の実装完了とは別に検収する．

成分の`eligible_cost_must_exceed_grant`は省略・falseなら従来挙動を保持する．trueは費目・税区分を指定した容量単価式に限り，容量処理・単価・上限・円丸め後の補助額を，未丸めの対象費用が厳密に上回る場合に採用する．既存の費用上限処理より先に判定し，同額以下の成分は`eligible_cost_not_above_grant`で除外する．他の適格成分は維持し，全成分不適格なら候補ではなく対象外とする．費用欠損は0円に置換せず入力エラーとして扱う．初期契約では丸め繰越，`formula_scope_totals`及び`formula_total`との併用を禁止する．札幌への正式採用は機能実装とは別工程とする．

最低対象費用の`eligible_cost_min_scope`は`solar`・`battery`・`battery_equipment`・`combined`から指定し，省略時は既存の`cost_scope`を使う．最低額の判定だけを独立させ，税区分は`cost_tax`を共有する．補助率・設備別上限・他補助控除は従来の`cost_scope`を維持する．網走の合成契約ではPV単独はPV費，併設はPV・蓄電池の合計費が税込10万円以上かを判定し，補助額は設備別1/10・各10万円上限・千円未満切捨てとする．入力外の工事費を補完しない．正式な網走データへの採用・表示確認は別工程とする．

## 利用可否

> **結論：公開データの読込または版の整合性確認に失敗した場合，計算ボタンを無効にする．**

`data_version`が`uninitialized`である場合，公開データとメタデータの版が一致しない場合，または計算処理が未実装の場合は，利用できない理由を画面に表示する．

## ローカル開発

> **結論：通常の画面開発はViteで行い，ビルドは変更の検査に必要な場合，デプロイは公開承認後に行う．**

既存の同用途サーバーを確認して再利用し，未起動の場合はリポジトリルートで`pnpm run dev`を実行する．HTMLファイルの直接表示ではなく，`http://localhost:5173/`を確認する．JavaScript ES ModulesとJSON読込を使用するため，ローカルサーバーを経由しない表示は正式な確認方法としない．`localhost:5173`はローカルサーバーの稼働中だけ利用できる．

画面開発を継続している間は，ローカルサーバーと`node_modules/`を維持する．`dist-pages/`はPages用，`dist/`および`.wrangler/`は従来検証用の生成物であり，通常のUI確認には使用しない．

| タイミング | 実施内容 |
|---|---|
| UI・文章・導線の反復中 | `pnpm run dev`によるローカル確認 |
| 複数の変更が確認可能な単位として固まった時点 | 影響範囲の自動検査（公開用とbackend依存のローカル監査QAを区別） |
| 公開可能な単位が完成した時点 | `pnpm run build:pages`によるGitHub Pages公開成果物の検査 |
| 必要な検収を終え，ユーザーが公開を明示承認した場合 | GitHub Pagesへの手動デプロイ（下記の公開手順） |

検収の実施タイミングと公開権限は[AI分業](../../../business-research/運営/AI分業.md#検収代理承認完了条件)，補助プロセスの管理は[root AGENTS](../../../AGENTS.md#プロセスのライフサイクル)に従う．

## テスト

> **結論：計算，公開データ，HTML構造および内部リンクを，依存ライブラリを追加せずNode.js標準テストで確認する．**

`pnpm run test:public`はfrontend内の公開データ・LFS取得済みfixtureだけで，計算・記事・サイト整合・トップ入力・ガイド・GA4を検査する．`pnpm run test:local-review`は隣接backendの監査原本・投影を必要とするローカル専用QAである．`pnpm test`は両者を順に実行し，どちらかが失敗すれば失敗とする．対象ケースと実画面確認の範囲は[QA](../../qa/README.md#必須ケースと検査範囲)，計算式と丸め規則はbackendの計算仕様を正本とする．

## GitHub Pagesの公開準備

> **結論：正式URLはhttps://haretoku.jpとし，Pages専用ビルドのdist-pagesだけを手動承認後に公開する．**

MUST：本番はGitHub Pages．既存Sites／Cloudflare設定はローカル開発・従来検証用であり，本番公開へ使わない．`pnpm run build:pages`は専用`vite.pages.config.js`で静的HTML・依存資産のみ生成し，sitemap.xml，robots.txt，.nojekyll，CNAME及び共通OGP画像を追加する．生成後のverify-pages.jsが正規9URL，参照資産，受領版schema_version=11.46.0の公開データ原バイト一致，開発用資料の非混入を検査する．公開対象はTOP，ガイド，診断，4記事，方針，計算方法，旧費用記事の転送ページと404．QA・監査・MD・Sites設定・Workerは同梱しない．

正規URLは`/`，`/guides/`，`/guides/<記事名>/`，`/simulator/`，方針・計算根拠の`/pages/*.html`とする．旧ガイドURLは下記「ガイドURLの移転互換」に従う．診断クエリーは状態復元用でcanonical／sitemapから除く．旧costs-maintenance.htmlは既存JS転送と手動リンクを維持しnoindex，canonicalは収支記事へ向ける．GitHub Pagesに任意のHTTPリダイレクト規則は置かず，旧/pages/の拡張子なしURLを正規経路として案内しない．404は未知URLをTOPへ転送せず復帰先を示す．

`pnpm run preview:pages --host 127.0.0.1 --port 4173 --strictPort`で成果物を検査する．設定はappType=mpaとし未知URLを200でTOPへ落とさない．Viteプレビューの404応答と，GitHub Pagesが404.html本文を返す動作は別に確認する．既存5173は開発用として保持し，補助プレビューは検収後に停止する．

### 公開時だけ行う手順

1. 対象commitと公開データ版・検収結果を固定し，統括の独立検収とユーザーの公開承認を得る．以下のドメイン・メール・環境設定は初回又は設定変更時に確認し，通常更新で再設定しない．
2. 初回又は設定変更時はcontact@haretoku.jpの実送受信を確認し，リポジトリSettings > PagesのSourceをGitHub Actions，Custom domainをharetoku.jpに設定する．Actions公開ではCNAMEファイルだけでCustom domainは設定されない．ドメイン所有確認とgithub-pages環境の承認・ブランチ制限を設定する．秘密情報や内部監査資料のリポジトリ公開可否はサイト成果物検査とは別に確認する．
3. 承認されたDNS変更時にapexのPagesレコードとwww→haretoku.github.ioを設定する．既存メール用MX／TXTを消さない．証明書発行後にEnforce HTTPSを有効化する．apex正規・www転送を実機確認する．
4. `.github/workflows/pages.yml`を手動実行し，検収済みrefを選び，確認欄へpublishを入力する．push／PRだけでは公開しない．build jobはtest:publicとbuild:pagesを通し，dist-pagesだけをupload-pages-artifactへ渡す．deploy jobのみpages:write／id-token:writeを持つ．
5. 公開URLで主要9ページ，旧費用記事転送，深い未知URLの404状態と復帰リンク，sitemap／robots／OGP画像，診断の入力→結果・条件復元・未収録表示，準備中見積もりの非表示，PC／スマホ表示を確認する．ローカルPASSを本番確認済みと扱わない．

公開成功後は実際に公開したcommitへ`v`タグを付ける．未公開の保存地点には`checkpoint/`を使い，[READMEのタグ規則](../../README.md#コミットタグと公開の区別)に従う．

### 切り戻し

公開ごとに対象commit，データ版，Actions実行IDと直前の成功refを運営側で記録する．問題があれば公開承認の範囲を確認し，直前の成功版を指す承認済みbranch／tagを選んで同じ手動workflowを再実行する．Actions UIから任意commit SHAを直接選べるとは扱わず，成功版のbranch／tagは別途承認されたGit操作で保持する．コードと同梱データを一緒に戻し，データだけ新しくしない．初回公開で復旧先がない場合は公開停止を判断する．DNS・メールはこの操作に含めない．切り戻しの実施結果は運営側で記録し，手順の記述だけで復旧確認済みとは扱わない．

根拠：[GitHubのカスタムworkflow](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages)，[独自ドメイン](https://docs.github.com/en/pages/configuring-a-custom-domain-for-your-github-pages-site/managing-a-custom-domain-for-your-github-pages-site)，[HTTPS](https://docs.github.com/en/pages/getting-started-with-github-pages/securing-your-github-pages-site-with-https)．

## GA4の接続準備と計測範囲

> **結論：測定ID未設定では送信せず，本番Pages配信・ホスト・設定確認を満たした場合だけ必要なイベントを計測する．**

2026年9月25日に統括から測定ID `G-CK29TBEBPC`を受領した．ストリームIDは15842815942，名前は「はれトク Web」，URLはhttps://haretoku.jp．統括による管理画面確認結果は，拡張計測マスターOFF，Googleシグナル・ユーザー提供データ収集未有効，広告パーソナライズ全307地域不許可，任意のアカウントデータ共有4項目OFF．ユーザーの計測準備承認に基づき，公開候補のenabled=true，enhancedMeasurementDisabled=trueとGA4利用のポリシー説明を揃えた．通常ローカルではタグ・キューを作らず，計測通信を発生させない．実Google collectとGA4到着の確認結果は運営側の検収を参照し，設定値だけで到達済みと判断しない．Search Consoleの所有確認は統括のDNS作業であり，サイト側に検証タグやGoogleログイン情報を埋め込まない．

有効化には，Pages専用ビルド，HTTPSの正確なharetoku.jp（www・非標準ポート不可），既存9ページとデータ2ページの許可リスト，形式が正しい測定ID，enabled=true，enhancedMeasurementDisabled=trueの全条件を要する．localhost，IP，開発サーバー，旧Sitesビルド，404・旧転送ページでは計測しない．有効化前にポリシーのdata-analytics-policyをenabledへ更新し，未導入という説明を実際のGA4使用へ書き換える．ビルド検査が状態不一致を拒否する．測定IDは公開識別子であり，Googleアカウントの認証情報ではない．

| イベント | 発火と集計上の意味 |
|---|---|
| page_view | 許可された各ページの読込ごとに手動で1回．診断の再計算は追加しない |
| article_view | 公開4記事の読込ごとに1回．page_idで記事を区別する |
| data_diagnosis_click | データページ内の自サイト診断リンクが押された時，その画面で1回．地域・受付フィルタ・リンク先URLは送信しない |
| article_diagnosis_click | 記事内の自サイト診断リンクが押された時，その記事画面で1回．全流入の診断開始とは異なる |
| diagnosis_complete | 有限な収支を持つ結果が正常に描画・表示された後，その診断画面で初めて1回．未入力・エラーは対象外．条件再計算やシナリオ変更で増やさない |

データTOP・補助金一覧はpage_viewで区別し，診断への移動はdata_diagnosis_clickで記事経由と区別する．フィルタ変更による追加page_viewは発生させない．データのnoindex・サイトマップ非掲載と本番公開の承認は計測対象への追加とは別管理とする．

結果表示の総数にはTOP・直接流入も含むため，全体diagnosis_completeを記事クリック数で割らない．GA4の探索ではarticle_view→article_diagnosis_click→diagnosis_completeという同じ訪問内の順序で絞って記事経由の到達を見る．独自のユーザーIDや入力値による紐付けはしない．新しいページ読込・リロードは別の画面として数えるため，人数や永続的な診断件数とは呼ばない．通信遮断・遷移離脱ではイベントが欠測し得る．未提携の見積もりはイベントを設けない．

送信する独自情報は固定のpage_idのみ．page_locationは定義済み正規パス，page_titleは固定名，page_referrerは自サイトの既知パス又は外部originだけとし，query／hashを除く．氏名・メール・自治体・電気代・設備条件・診断金額・クリック先URL・画面の入力値をイベント引数に渡さない．utmキャンペーン値も空で上書きする．GoogleタグscriptのreferrerPolicyはno-referrer．広告用storage／user_data／personalizationはdenied，allow_google_signalsとallow_ad_personalization_signalsはfalseとする．analytics_storageは有効化時にgrantedであり，Cookieを用いる通常のGA4計測になる．必要な同意方針を変更する場合は有効化前に実装を合わせる．

### GA4画面で確認してから有効にする項目

- 拡張計測を全OFF．特にページ履歴（pushState／replaceState／popstate）によるpage_view，フォーム，検索，外部クリック，自動イベント検出を有効にしない．send_page_view=falseだけでは履歴イベントを防げないため，未確認では確認フラグを立てない．管理画面で後からONにすると保護の前提が崩れるので，設定変更時も再検査する．
- Google signals，広告パーソナライズ，ユーザー提供データの収集，Google広告連携・クロスドメイン設定は使わない．意図しない自動イベント／追加タグの設定がないことを確認する．プロパティのタイムゾーン・通貨は日本／円を確認する．
- ポリシーにGoogle Analyticsの利用目的（記事から診断への到達と結果表示の改善），Cookie等による利用状況の収集，診断入力条件をGA4へ送らない設計，Googleの取扱い・無効化手段を説明する．未設定状態では現行の未導入表記を維持する．
- 測定ID受領後に確認フラグとポリシーを揃え，ローカルでは引き続き外部計測ゼロを検査する．本番公開後に標準のブラウザ通信検査でcollectのdl/dr・追加パラメータにquery／hash／入力値がないこと，拡張計測による追加page_viewがないこと，GA4リアルタイム／DebugViewでイベントの順序・重複を確認する．ローカル検査は実Googleタグの通信・GA4到着の確認を代替しない．
