# 実装方針

## 文書の位置付け

> **結論：本文書は，画面設計とbackendの公開仕様を，frontendの技術構成，モジュール分担，データ境界および検査手順へ具体化する．**

サービス範囲と事業要件は`business-research`，利用者体験とページ責務は[グランドデザイン](グランドデザイン.md)，表示・操作・文言は[画面設計](画面設計.md)，計算式と公開データは`backend`を正本とする．本文書では，これらの内容を変更せず，実装上の分担と手順だけを定める．文書体系全体は[frontend README](../../README.md#文書体系)を参照する．

## 基本方針

> **結論：MVPは，静的サイトとしてブラウザ内の計算と事前生成データで完結させる．**

サイト本体にはHTML，CSSおよびブラウザ実行時の依存ライブラリを持たないJavaScript ES Modulesを使用する．確認用公開と複数HTMLの成果物生成に限ってViteおよびCloudflare Workers互換設定を使用するが，実行時のサーバー処理，データベースおよびクラウド関数は使用しない．

公開リポジトリには秘密情報，APIキー，非公開データおよび内部処理用データを置かない．未確定の計算式または未検証のデータから採算値を生成せず，得にならない結果もそのまま表示し，採算が良く見えるように前提を変更しない．

必要性が確定するまで，フレームワーク，サーバー，データベースおよび外部解析サービスを追加しない．

## URL設計

> **結論：新規領域は，住宅エネルギー分野を表す次のトップレベルURLへ分類する．**

| トップレベルURL | 対象領域 |
|---|---|
| `/solar/` | 太陽光，蓄電池，V2H・EV |
| `/hot-water/` | エコキュート，ガス給湯，エネファーム等の給湯・熱源 |
| `/insulation/` | 断熱，窓 |
| `/energy-plans/` | 電力・ガス料金プラン |
| `/diagnosis/` | 住宅エネルギー総合診断 |

これらを情報分類上の正規の大分類とし，新規に追加するページと機能は該当するトップレベルURLの下へ配置する．既存URLの移動，リダイレクト，canonical，サイトマップおよび内部リンクの変更は本文書化の対象外とし，既存URLの扱いは別途移行判断する．

現行の住宅用太陽光に関する「はれトクガイド」一覧は`/solar/`とする．太陽光領域の入口として記事を横断して探せる一方，既存記事の`/pages/*.html`は移動せず，互換性を維持する．

## JavaScriptの分担

> **結論：画面制御，公開データ読込および採算計算を分離する．**

| ファイル | 役割 |
|---|---|
| `site/simulator/src/top.js` | トップの初期化，入力制御，利用可否の表示および診断画面への遷移 |
| `site/simulator/src/app.js` | 診断画面の初期化，条件変更，結果表示および各処理の接続 |
| `data/src/data-loader.js` | 公開データの取得と版の整合性確認 |
| `site/simulator/src/calculator.js` | backend仕様と一致するブラウザ採算計算 |
| `site/articles/src/article-data.js` | 詳細記事への採用値と出典の反映 |

都道府県選択肢は`data/input/public-data.json`から生成し，frontend内に同じ一覧を重複して保持しない．

## backend連携

> **結論：実行時データは`data/input/`，backendとの一致確認専用データは`qa/fixtures/`へ分離する．**

| ファイル | 用途 |
|---|---|
| `data/input/public-data.json` | ブラウザ計算に必要な公開データ |
| `data/input/metadata.json` | スキーマ版，データ版，生成日時および出典概要 |
| `qa/fixtures/calculation-cases.json` | frontend計算とbackend基準計算の一致確認 |

公開データとメタデータの`schema_version`および`data_version`が一致しない場合は，計算機能を有効にしない．秘密情報またはbackendの内部データへ直接接続しない．

## 利用可否

> **結論：公開データの読込または版の整合性確認に失敗した場合，計算ボタンを無効にする．**

`data_version`が`uninitialized`である場合，公開データとメタデータの版が一致しない場合，または計算処理が未実装の場合は，利用できない理由を画面に表示する．

## ローカル開発

> **結論：通常の画面開発はViteのローカルサーバー上で行い，公開単位が完成するまでビルドおよびデプロイを行わない．**

既存の同用途サーバーを確認して再利用し，未起動の場合はリポジトリルートで`pnpm run dev`を実行する．HTMLファイルの直接表示ではなく，`http://localhost:5173/`を確認する．JavaScript ES ModulesとJSON読込を使用するため，ローカルサーバーを経由しない表示は正式な確認方法としない．`localhost:5173`はローカルサーバーの稼働中だけ利用できる．

画面開発を継続している間は，ローカルサーバーと`node_modules/`を維持する．`dist/`および`.wrangler/`は公開ビルド時の生成物であり，通常のUI確認には使用しない．

| タイミング | 実施内容 |
|---|---|
| UI・文章・導線の反復中 | `pnpm run dev`によるローカル確認 |
| 複数の変更が確認可能な単位として固まった時点 | `pnpm test`による自動検査 |
| 公開可能な単位が完成した時点 | `pnpm run build:pages`によるGitHub Pages公開成果物の検査 |
| 必要な検収を終え，ユーザーが公開を明示承認した場合 | GitHub Pagesへの手動デプロイ（本節の公開手順） |

検収の実施タイミングと公開権限は[AI分業](../../../business-research/運営/AI分業.md#検収代理承認完了条件)，補助プロセスの管理は[root AGENTS](../../../AGENTS.md#プロセスのライフサイクル)に従う．

## テスト

> **結論：計算，公開データ，HTML構造および内部リンクを，依存ライブラリを追加せずNode.js標準テストで確認する．**

`pnpm run test:public`はfrontend内の公開データ・LFS取得済みfixtureだけで，計算・記事・サイト整合・トップ入力・ガイド・GA4を検査する．`pnpm run test:local-review`は隣接backendの監査原本・投影を必要とするローカル専用QAである．`pnpm test`は両者を順に実行し，どちらかが失敗すれば失敗とする．対象ケースと実画面確認の範囲は[QA](../../qa/README.md#必須ケースと検査範囲)，計算式と丸め規則はbackendの計算仕様を正本とする．

## GitHub Pagesの公開準備

> **結論：正式URLはhttps://haretoku.jpとし，Pages専用ビルドのdist-pagesだけを手動承認後に公開する．**

MUST：本番はGitHub Pages．既存Sites／Cloudflare設定はローカル開発・従来検証用であり，本番公開へ使わない．`pnpm run build:pages`は専用`vite.pages.config.js`で静的HTML・依存資産のみ生成し，sitemap.xml，robots.txt，.nojekyll，CNAME及び共通OGP画像を追加する．生成後のverify-pages.jsが正規9URL，参照資産，佐賀schema_version=11.17.0の公開データ原バイト一致，開発用資料の非混入を検査する．公開対象はTOP，ガイド，診断，4記事，方針，計算方法，旧費用記事の転送ページと404．QA・監査・MD・Sites設定・Workerは同梱しない．

正規URLは`/`，`/solar/`，`/simulator/`，`/pages/*.html`．既存記事の.htmlを維持し，相対参照の階層を変えない．診断クエリーは状態復元用でcanonical／sitemapから除く．旧costs-maintenance.htmlは既存JS転送と手動リンクを維持しnoindex，canonicalは収支記事へ向ける．GitHub Pagesに任意のHTTPリダイレクト規則は置かず，拡張子なし記事URLを正規経路として案内しない．404は未知URLをTOPへ転送せず復帰先を示す．

`pnpm run preview:pages --host 127.0.0.1 --port 4173 --strictPort`で成果物を検査する．設定はappType=mpaとし未知URLを200でTOPへ落とさない．Viteプレビューの404応答と，GitHub Pagesが404.html本文を返す動作は別に確認する．既存5173は開発用として保持し，補助プレビューは検収後に停止する．

### 公開時だけ行う手順

1. 対象commitと公開データ版・検収結果を固定し，統括の独立検収とユーザーの公開承認を得る．contact@haretoku.jpのDNS反映・実送受信を確認する．
2. リポジトリSettings > PagesのSourceをGitHub Actions，Custom domainをharetoku.jpに設定する．Actions公開ではCNAMEファイルだけでCustom domainは設定されない．ドメイン所有確認とgithub-pages環境の承認・ブランチ制限を設定する．秘密情報や内部監査資料のリポジトリ公開可否はサイト成果物検査とは別に確認する．
3. 承認されたDNS変更時にapexのPagesレコードとwww→haretoku.github.ioを設定する．既存メール用MX／TXTを消さない．証明書発行後にEnforce HTTPSを有効化する．apex正規・www転送を実機確認する．
4. `.github/workflows/pages.yml`を手動実行し，検収済みrefを選び，確認欄へpublishを入力する．push／PRだけでは公開しない．build jobはtest:publicとbuild:pagesを通し，dist-pagesだけをupload-pages-artifactへ渡す．deploy jobのみpages:write／id-token:writeを持つ．
5. 公開URLで主要9ページ，旧費用記事転送，深い未知URLの404状態と復帰リンク，sitemap／robots／OGP画像，診断の入力→結果・条件復元・未収録表示，準備中見積もりの無効状態，PC／スマホ表示を確認する．ローカルPASSを本番確認済みと扱わない．

### 切り戻し

公開ごとに対象commit，データ版，Actions実行IDと直前の成功refを運営側で記録する．問題があれば公開承認の範囲を確認し，直前の成功版を指す承認済みbranch／tagを選んで同じ手動workflowを再実行する．Actions UIから任意commit SHAを直接選べるとは扱わず，成功版のbranch／tagは別途承認されたGit操作で保持する．コードと同梱データを一緒に戻し，データだけ新しくしない．初回公開で復旧先がない場合は公開停止を判断する．DNS・メールはこの操作に含めない．GitHub上のworkflow実行・切戻しは未実施で，本番時に確認する．

根拠：[GitHubのカスタムworkflow](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages)，[独自ドメイン](https://docs.github.com/en/pages/configuring-a-custom-domain-for-your-github-pages-site/managing-a-custom-domain-for-your-github-pages-site)，[HTTPS](https://docs.github.com/en/pages/getting-started-with-github-pages/securing-your-github-pages-site-with-https)．

## GA4の接続準備と計測範囲

> **結論：測定ID未設定では送信せず，本番Pages配信・ホスト・設定確認を満たした場合だけ必要なイベントを計測する．**

2026年9月25日に統括から測定ID `G-CK29TBEBPC`を受領した．ストリームIDは15842815942，名前は「はれトク Web」，URLはhttps://haretoku.jp．統括による管理画面確認結果は，拡張計測マスターOFF，Googleシグナル・ユーザー提供データ収集未有効，広告パーソナライズ全307地域不許可，任意のアカウントデータ共有4項目OFF．ユーザーの計測準備承認に基づき，公開候補のenabled=true，enhancedMeasurementDisabled=trueとGA4利用のポリシー説明を揃えた．この変更はローカルの公開候補作成であり，commit／push／deployは含まない．通常ローカルではタグ・キューを作らず，計測通信を発生させない．実Google collectの通信内容とGA4到着は，本番公開後の確認として未検証である．Search Consoleの所有確認は統括のDNS作業であり，サイト側に検証タグやGoogleログイン情報を埋め込まない．

有効化には，Pages専用ビルド，HTTPSの正確なharetoku.jp（www・非標準ポート不可），許可された公開9ページ，形式が正しい測定ID，enabled=true，enhancedMeasurementDisabled=trueの全条件を要する．localhost，IP，開発サーバー，旧Sitesビルド，404・旧転送ページでは計測しない．有効化前にポリシーのdata-analytics-policyをenabledへ更新し，未導入という説明を実際のGA4使用へ書き換える．ビルド検査が状態不一致を拒否する．測定IDは公開識別子であり，Googleアカウントの認証情報ではない．

| イベント | 発火と集計上の意味 |
|---|---|
| page_view | 許可された各ページの読込ごとに手動で1回．診断の再計算は追加しない |
| article_view | 公開4記事の読込ごとに1回．page_idで記事を区別する |
| article_diagnosis_click | 記事内の自サイト診断リンクが押された時，その記事画面で1回．全流入の診断開始とは異なる |
| diagnosis_complete | 有限な収支を持つ結果が正常に描画・表示された後，その診断画面で初めて1回．未入力・エラーは対象外．条件再計算やシナリオ変更で増やさない |

結果表示の総数にはTOP・直接流入も含むため，全体diagnosis_completeを記事クリック数で割らない．GA4の探索ではarticle_view→article_diagnosis_click→diagnosis_completeという同じ訪問内の順序で絞って記事経由の到達を見る．独自のユーザーIDや入力値による紐付けはしない．新しいページ読込・リロードは別の画面として数えるため，人数や永続的な診断件数とは呼ばない．通信遮断・遷移離脱ではイベントが欠測し得る．未提携の見積もりはイベントを設けない．

送信する独自情報は固定のpage_idのみ．page_locationは定義済み正規パス，page_titleは固定名，page_referrerは自サイトの既知パス又は外部originだけとし，query／hashを除く．氏名・メール・自治体・電気代・設備条件・診断金額・クリック先URL・画面の入力値をイベント引数に渡さない．utmキャンペーン値も空で上書きする．GoogleタグscriptのreferrerPolicyはno-referrer．広告用storage／user_data／personalizationはdenied，allow_google_signalsとallow_ad_personalization_signalsはfalseとする．analytics_storageは有効化時にgrantedであり，Cookieを用いる通常のGA4計測になる．必要な同意方針を変更する場合は有効化前に実装を合わせる．

### GA4画面で確認してから有効にする項目

- 拡張計測を全OFF．特にページ履歴（pushState／replaceState／popstate）によるpage_view，フォーム，検索，外部クリック，自動イベント検出を有効にしない．send_page_view=falseだけでは履歴イベントを防げないため，未確認では確認フラグを立てない．管理画面で後からONにすると保護の前提が崩れるので，設定変更時も再検査する．
- Google signals，広告パーソナライズ，ユーザー提供データの収集，Google広告連携・クロスドメイン設定は使わない．意図しない自動イベント／追加タグの設定がないことを確認する．プロパティのタイムゾーン・通貨は日本／円を確認する．
- ポリシーにGoogle Analyticsの利用目的（記事から診断への到達と結果表示の改善），Cookie等による利用状況の収集，診断入力条件をGA4へ送らない設計，Googleの取扱い・無効化手段を説明する．未設定状態では現行の未導入表記を維持する．
- 測定ID受領後に確認フラグとポリシーを揃え，ローカルでは引き続き外部計測ゼロを検査する．本番公開後に標準のブラウザ通信検査でcollectのdl/dr・追加パラメータにquery／hash／入力値がないこと，拡張計測による追加page_viewがないこと，GA4リアルタイム／DebugViewでイベントの順序・重複を確認する．実Googleタグの外部通信とGA4到着は，ローカルの公開候補検査では未検証である．

根拠：[GA4手動page_viewと履歴計測](https://developers.google.com/analytics/devguides/collection/ga4/views)，[GA4設定フィールド](https://developers.google.com/analytics/devguides/collection/ga4/reference/config)，[拡張計測の設定](https://support.google.com/analytics/answer/9216061?hl=en)．

ポリシー説明の根拠：[Googleの連携サイト情報の使用](https://policies.google.com/technologies/partner-sites?hl=ja)，[プライバシーポリシー](https://policies.google.com/privacy?hl=ja)，[オプトアウトアドオン](https://tools.google.com/dlpage/gaoptout?hl=ja)．


## 公開ビルドのCSS順序

> **結論：共通main，記事ベースarticle，ページ固有CSSの順を生成HTMLで保持し，ビルド検査で逆転を拒否する．**

v0.1.2では，Viteの共有CSS分割によるlink順序の逆転をfinalize-pages.jsで補正する．固有CSS同士の順序と資産自体は変更しない．verify-pages.jsは全HTMLでこの順序を検査する．ソースHTMLの順だけを根拠に表示を保証せず，公開生成物を配信したPC・360pxの診断，TOP，ガイド，代表記事を実画面で確認する．
