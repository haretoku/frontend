## 検収の段階

> **結論：本書はfrontendの検査範囲・合格条件・結果を定め，担当・実施タイミング・完了承認はAI分業に従う．**

3段階の分担は[運営方針の診断の3段階検収](../../business-research/運営/運営方針.md#診断の3段階検収)，独立レビューの実施条件は[検収・代理承認・完了条件](../../business-research/運営/運営方針.md#検収代理承認完了条件)を参照する．①・②の検証は[backend QA方針](../../backend/qa/docs/QA方針.md)が定める．frontendとPythonの共通ケース一致確認（`tests/`と`fixtures/`）は②の連携検査であり，公式根拠・算式の独立検証とは区別する．

計算処理または計算に関係するデータ連携を変更する場合は，frontend QAを実行し，backend基準計算ケースとの一致を確認する．見た目，レイアウトまたは導線の変更は，自動テストだけで完了とせず，実ブラウザで確認する．検査するケースと範囲は「必須ケースと検査範囲」に従う．

表示文言，分類，配置および操作の詳細は[画面設計](../site/docs/画面設計.md)を正本とし，本書へ重複転記しない．画面設計を変更した場合は，その規則に対応する以下の検査項目と適用ケースを見直す．

一般向けガイド記事は，[記事制作のレビューの確認観点](../../business-research/運営/運営方針.md#レビューの確認観点)に従い，設計への適合，導入の概要・分解と後続章・節の対応，章・節・段落の説明の十分さ，読む流れを保つ短い根拠説明を確認する．HTML・数値・リンク等の機械検査のPASSだけで記事の内容レビューを完了にしない．内容の合否，実表示・操作の確認範囲及び未確認事項は，対象版とともに担当チャットで簡潔に報告する．

## ③計算結果と実画面の必須検査

> **結論：同じデータ版・画面コード版・入力の計算結果を実ブラウザの表示と照合し，以下の項目をすべて満たすことを合格条件とする．**

| 検査項目 | 必須の照合と合格条件 |
|---|---|
| 制度の対応 | 算入・候補・非算入の計算記録と画面の制度を照合する．旧ID，同制度の重複，対象地域外の制度の混入がなく，住宅・設備等の不一致による正当な非算入制度を誤って削除していない．採否未確定の参考情報を採用・非採用と断定しない． |
| 制度名・金額・受付 | 制度名，金額の意味，未確定値，公式リンクが正本に対応し，複数枠の制度では採用枝の受付状態と一致する．公開データと計算結果の受付enumに未対応値がなく，混在状態を一律に受付中へ変換しない． |
| 非算入理由 | 入力フィルター（診断範囲外を含む）→受付状態→明示的な併用禁止・対象費用上限→算定詳細不明の優先順に，根拠のある理由を1件だけ示す．未確認の併用を禁止，未確定額を金額比較による不選択と読み替えない． |
| 表示内容 | 画面設計で廃止した文言，内部事情，カード内の詳細列挙が残っていない．集約先の条件・注意事項と公式情報へのリンクが機能する． |
| 条件変更 | 地域，住宅区分，設備，容量を変更し，再計算後の金額・制度・受付・理由・要約に旧入力の表示が残らない．編集の反映・取消，URL復元も画面設計に従う． |
| シナリオ変更 | 同じ入力における基準の適用想定制度・制度額・利用想定の階層合計は維持する．今回の実算入欄・非算入理由・分類と財務・グラフは選択シナリオに連動し，下振れの実算入は0円，正額候補は参考額へ分離する． |
| 開閉・操作・画面幅 | PCとスマートフォンで初期開閉状態，個別の開閉，条件変更後の状態，内訳への導線・フォーカス，キーボード操作を確認する．共通注意の位置・回数を含め，文字・金額・リンクの欠け，重なり，横はみ出しがない． |

## 必須ケースと検査範囲

> **結論：新しい計算表示パターン・状態・境界は必ず実画面で確認し，既存パターンだけの地域追加は自動検査と代表実画面の組合せで確認できる．**

スマートフォンの配置変更は360／412 pxの両設備で，結果位置，終点ラベル，横はみ出し，条件の反映・取消・URL復元，グラフ詳細・フォーカス復帰，収支・電力量・容量根拠の開閉を確認する．固定見積もりバーは2026年10月2日の常時表示承認に従い，初期・未診断・編集・入力フォーカス・グラフ詳細・本文CTA可視でも表示を維持し，下端余白，フォーカス対象の可視性，グラフ戻りと右上ガイドの到達を確認する．PCの4条件カードと固定バー，ガイド5記事の導入末尾・目次アンカー・末尾，対象ページの本文見積もりボタン削除，TOP本文CTA保持と全ページの共通バー入口の一意性と，本番ASP未接続時のバー非生成も確認し，ブラウザ幅検査と実端末検査を区別する．

新規または変更されたパターンについて，適用される次のケースを選ぶ．新しい受付enum，採用枝，非算入理由，未確定値，容量下限・端数処理・上限等の境界は省略しない．

- 採用・非採用・候補・参考情報，空一覧，未調査・未収録を区別できるケース．
- 新築・既存，両設備構成，地域変更，容量境界の直前・一致・直後で制度の表示または計算結果が変わるケース．
- 受付中・終了・停止・開始前・補欠・未確認，および複数枠から採用枝を選ぶケース．
- 入力不一致と受付終了等が重なるケース，明示併用禁止，対象費用上限，併用未確認，算定詳細不明を区別するケース．
- 国・47県のみの診断，旧cityクエリーの無視，県の地域限定条件を判定できない場合の非算入候補，受付と未確定の区別，URL保存・復元．
- 同じ入力での全シナリオ切替，初期表示，開閉後の条件変更，編集反映・取消，URL復元を含むケース．

適用ケースはPCとスマートフォンで確認する．現行の代表幅はPC 1280 pxとスマートフォン360 pxとし，表示に関係する境界幅を変更した場合はその前後も対象とする．既存の計算・表示パターンだけを使う地域追加では，追加地域の自動照合と同じパターンの代表実画面確認を行い，代表ケースで覆える根拠を示す．新パターンが含まれる場合はこの省略を適用しない．全件再検証を一律に要求せず，変更の影響範囲と未検証の状態を明示する．

## 検査対象の識別と結果報告

> **結論：検査結果は既存の担当タスクから統括へ報告し，対象版・入力・担当・合否・残件を追跡できる形で結び付ける．**

報告には次を含める．新しい台帳や検収ファイルを作成しない．

- データ版と使用した公開成果物・fixtureのハッシュ．
- 画面コード版．コミット済みならコミットID，未コミット変更を含む場合は検査したファイルのパスと内容ハッシュを用い，コミットIDだけで識別しない．
- 再現できる入力ケースの参照．既存fixtureのケースIDと入力定義への参照を優先し，変更した入力，既定値の使用，URL復元条件，操作順，画面幅を識別する．入力値を報告へ再掲しない制約がある場合も，既存の入力定義・担当タスクへの参照を残す．
- 実装担当と検収担当，検査日時，段階別の合否，対象外・未検証の範囲，残件．

別のデータ版・画面コード版・入力条件のPASSを，現在の対象のPASSとして流用しない．既存確認を参照する場合は元の対象を明示し，変更後の対象について必要な照合と代表実画面検査を行う．一時ログ・画像・比較データは確認後に削除し，繰り返し必要なケースは既存テスト・fixture，継続的な規則は対応する正本文書へ反映する．
