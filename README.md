# frontend

はれトクの公開Webサイトです．

## 目的

> **結論：frontendは，「太陽光，結局いくらトク？」に対し，概算結果，根拠および見積もり導線を順に示す静的Webサイトである．**

`business-research`のサービス要件と，`backend`の計算・データ仕様を表示可能な形にする．住宅用太陽光の導入を一律に推奨せず，得にならない概算結果もそのまま表示する．

3リポジトリを横断する担当範囲，依頼および完了承認は，[business-researchのAI分業](../business-research/運営/AI分業.md)を正本とする．

## 文書体系

> **結論：business-researchの要件を，グランドデザインでは利用者体験，画面設計では表示・操作，実装方針では技術構成へ具体化し，backendの公開データに基づいて実装する．**

| 文書・対象 | 定める内容 | 定めない内容 |
|---|---|---|
| `business-research` | サービス範囲，事業要件，計算対象および運営方針 | 具体的な計算式，データ項目，画面配置および寸法 |
| `backend` | 計算式，データ項目，検査基準およびfrontend向け公開成果物 | 利用者体験，画面配置および表示上の優先順位 |
| [グランドデザイン](site/docs/グランドデザイン.md) | 利用者体験，ページ責務，ブランド原則，成果指標および初期範囲 | CSS，寸法および部品状態 |
| [画面設計](site/docs/画面設計.md) | 画面構成，表示順，文言，導線，配色，フォント，寸法および操作 | サービス範囲，収益モデルおよびページ責務の変更 |
| [補助金データ](site/docs/補助金データ.md) | 補助金一覧固有のフィルタ，列，状態，導線および接続要件 | データ全体の掲載方針，正式なデータ項目・型 |
| [実装方針](site/docs/実装方針.md) | 技術構成，モジュール分担，データ境界，利用不能時の処理および開発コマンド | UX，文言，配色，計算式および採用データの変更 |
| 実装コード | 画面設計，実装方針およびbackend公開仕様を動作する形で実現する | 未合意の仕様判断 |

上位文書の方針と下位文書の具体指定が矛盾する場合は，上位文書を優先し，必要な判断を上位文書へ反映してから下位文書と実装を更新する．計算式と公開データはbackend，利用者体験とページ責務はグランドデザイン，表示・操作は画面設計，技術構成は実装方針，検査範囲・結果は[QA](qa/README.md)を正本とする．

一般向け記事の構成・目次・見出し・画像・章末補足は，[画面設計の「ガイド記事の本文構造」](site/docs/画面設計.md#ガイド記事の本文構造)を正本とする．

はれトクデータ全体の掲載・根拠・更新は[business-researchの掲載・更新方針](../business-research/運営/データ掲載・更新方針.md)，共通UIは[画面設計](site/docs/画面設計.md#ハレトクデータ)，補助金ページ固有の表示・操作は[補助金データ](site/docs/補助金データ.md)を正本とする．

## 構成

> **結論：frontendは，公開画面，backendから受け取る公開データおよび自動検査を分離する．**

| 場所 | 役割 |
|---|---|
| `site/` | シミュレーター，詳細記事，共通表示およびホスティング処理 |
| `data/` | backendの公開成果物の受取，読込および版確認 |
| `qa/` | backend基準ケース，計算，HTML，リンクおよび統合の検査 |

Vite，Wrangler，Sitesおよびパッケージ管理がルートから設定を発見できるよう，`.openai/`，`vite.config.js`，`wrangler.jsonc`および`package.json`はルートに置くが，責任上は`site`の公開処理に属する．詳細は[site](site/README.md)，[data](data/README.md)および[qa](qa/README.md)を参照する．

## 人間とAIの役割分担

> **結論：AIが実装，データ反映および自動検査を担当し，人間は公開画面のUX，文章，情報の優先順位および見た目を判断する．**

通常，人間がJSON，テストfixtureおよび実装コードを直接編集する運用は想定しない．`data/input/`はbackendが生成した公開成果物を受け取り，`qa/`は自動検査とbackend基準計算との一致確認を担当する．人間は実ブラウザで公開画面を確認し，UX，文章，情報の優先順位および見た目に関する判断を[画面設計](site/docs/画面設計.md)へ反映する．

## 文書・不要ファイルの整理方針

> **結論：整合性・簡潔さ・統一性・冗長さの排除を基準に，判断・実装・根拠確認に必要な文書とファイルを保持する．**

### 文書の記述とレビュー

分析・仕様文書では，各`##`の直下に原則一文の`> **結論：〜．**`を置き，必要な根拠・前提・限界を続ける．事実，採用方針，仮説及び未確認事項を区別し，数値には定義，対象期間，出典及び推計上の限界を付す．異なる役割の文書へ同じ構成を強制しない．

レビューでは，文書内・文書間の整合性，結論と説明の簡潔さ，用語・定義・表記の統一性，重複や古い経緯の有無を確認する．指摘には影響と最小限の修正案を添え，誤判断・誤作業につながる問題はMUST，読みやすさ・保守性はRECOMMEND，軽微な表記はNITSとする．判断に影響するMUSTを解消し，未確認事項と対応先を明示できれば完了とし，任意改善をゼロにするまで繰り返さない．

### 統合・削除

文書は「消すと判断・作業・根拠確認に困るか」で判定する．重複する詳細は上記の文書体系に従って正本へ集約し，重要な条件・根拠・未確認事項は残す．概要や注意の再掲は，その場所で読む意味があれば維持する．完了済みの作業経緯・旧案は必要な決定と制約を正本へ反映し，履歴はGitで追跡する．検収判定と版別QAの保持は下記の保持方針に従い，過去のPASSを現行版の合格へ転用しない．

不要ファイルは，名前や更新日だけで判断せず，実装の参照，動的・一括読込み，ビルド設定，テスト，公開URLの互換性及び稼働中の処理での利用を確認して削除する．未参照でも必要なQA基準データや受領原本は保持する．削除のために履歴用フォルダや新しい常設台帳を増やさない．

### 変更・確認の境界

- **MUST：編集と方針変更を分ける．** 最新の決定で解消できる矛盾は修正する．採用方針が不明な場合は確認し，整理を理由に採用済みの判断・数値・計算仕様を変更しない．
- **MUST：連携部分を確認する．** backendの公開成果物の受渡しパス，Schema・版確認，計算基準データ及びリポジトリ間の参照先を変える場合は，担当間で影響を確認する．文書や画像の整理だけを理由にデータを再同期しない．
- **MUST：確認範囲を明示する．** 文書間の整合，一次資料の再確認，実装・実画面の検証を区別し，実施した確認と残る未確認事項を報告する．変更に応じてリンク・ビルド・関連テスト・実画面を確認し，文書整理だけで全件再検査を始めない．
- **MUST：進行中の作業を保護する．** 未公開の変更，利用中の一時ファイル及び共有開発サーバーを確認し，別作業の成果物を不要と扱わない．

## ファイルの保持方針

> **結論：保持・清掃はAI分業を正本とし，frontend固有の資産と版別QA記録の扱いを補足する．**

共通の保持・清掃基準は[AI分業のファイル保持方針](../business-research/運営/AI分業.md#ファイルの保持方針)に従う．frontend固有の保持対象は，使用中の画像，受領した公開データと出典，QAの基準データ及び開発中の`node_modules/`とする．QAに記録した版別の検査実績は，現行の合格や作業指示と区別して保持する．

## コミット・タグと公開の区別

> **結論：通常のコミットにはタグを付けず，本番公開済みのコミットには`v`タグ，特別な保存地点には必要に応じて`checkpoint/`タグを付ける．**

- **MUST：公開版の識別．** `v<major>.<minor>.<patch>`（例：`v0.1.4`）は，本番公開の成功と対象コミットを確認してから，実際に公開したコミットへ付ける．公開前の候補や整理の保存地点には使わない．
- **MUST：作業用保存地点の識別．** 通常の開発はコミットだけで保存し，毎回のタグ作成は不要とする．整理・削除前など，復元地点を明示したい場合に限り，`checkpoint/YYYY-MM-DD-目的`（例：`checkpoint/2026-09-27-before-cleanup`）の注釈付きタグを使う．注釈に保存対象と範囲を記し，公開済み・検収済みを意味するものと扱わない．既存タグを別コミットへ付け替えない．
- **MUST：未コミット変更の区別．** タグはコミットを指し，作業中・未追跡のファイルを保存しない．削除前に復元対象がコミットへ含まれるか確認する．未コミット変更も保存する必要がある場合は，対象を分けてコミットし，特別な保存地点として明示する必要がある場合だけタグを付ける．
- **MUST：保存と公開を分離する．** 現行の[Pages公開設定](.github/workflows/pages.yml)は手動実行と`publish`入力で公開し，コミット・プッシュ・タグ作成だけでは公開しない．各操作の承認範囲はAI分業に従い，保存用タグを公開の承認に代用しない．

## 更新・確認手順

> **結論：開発コマンドは実装方針，検査範囲はQA，公開権限はAI分業を参照する．**

初回・依存関係更新時は`pnpm install`を実行する．日常の確認・ビルド手順は[ローカル開発](site/docs/実装方針.md#ローカル開発)，公開データの受領は[data](data/README.md)，検査範囲は[QA](qa/README.md#必須ケースと検査範囲)，公開処理は[site](site/README.md)を参照する．公開の承認・完了条件は[AI分業](../business-research/運営/AI分業.md#検収代理承認完了条件)に従う．開発・整理作業では，本番の`haretoku.jp`のDNSを変更しない．

Git LFSを導入した環境でcloneし，既存の作業コピーでは検査前に`git lfs install`と`git lfs pull`を実行する．LFS対象は`qa/fixtures/calculation-cases.json`のみで，ポインタではなくJSON本体を取得してから検査する．Pagesのcheckoutも`lfs: true`で取得する．
