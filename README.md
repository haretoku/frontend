# frontend

はれトクの公開Webサイトです．

## 目的

> **結論：frontendは，「太陽光，結局いくらトク？」に対し，概算結果，根拠および見積もり導線を順に示す静的Webサイトである．**

`business-research`のサービス要件と，`backend`の計算・データ仕様を表示可能な形にする．住宅用太陽光の導入を一律に推奨せず，得にならない概算結果もそのまま表示する．

3リポジトリを横断する担当範囲，依頼および完了承認は，[business-researchのAI分業](../business-research/運営/AI分業.md)を正本とする．

## 文書体系

> **結論：business-researchの要件を，グランドデザインでは利用者体験，画面設計では表示・操作，実装方針では技術構成へ具体化し，backendの公開データに基づいて実装する．**

| 文書・対象 | 定める内容 | 定めない内容 |
|---|---|---|
| `business-research` | サービス範囲，事業要件，計算対象および運営方針 | 具体的な計算式，データ項目，画面配置および寸法 |
| `backend` | 計算式，データ項目，検査基準およびfrontend向け公開成果物 | 利用者体験，画面配置および表示上の優先順位 |
| [グランドデザイン](site/docs/グランドデザイン.md) | 利用者体験，ページ責務，ブランド原則，成果指標および初期範囲 | CSS，寸法および部品状態 |
| [画面設計](site/docs/画面設計.md) | 画面構成，表示順，文言，導線，配色，フォント，寸法および操作 | サービス範囲，収益モデルおよびページ責務の変更 |
| [実装方針](site/docs/実装方針.md) | 技術構成，モジュール分担，データ境界，利用不能時の処理および開発コマンド | UX，文言，配色，計算式および採用データの変更 |
| 実装コード | 画面設計，実装方針およびbackend公開仕様を動作する形で実現する | 未合意の仕様判断 |

上位文書の方針と下位文書の具体指定が矛盾する場合は，上位文書を優先し，必要な判断を上位文書へ反映してから下位文書と実装を更新する．計算式と公開データはbackend，利用者体験とページ責務はグランドデザイン，表示・操作は画面設計，技術構成は実装方針，検査範囲・結果は[QA](qa/README.md)を正本とする．

一般向け記事の構成・目次・見出し・画像・章末補足は，[画面設計の「ガイド記事の本文構造」](site/docs/画面設計.md#ガイド記事の本文構造)を正本とする．

## 構成

> **結論：frontendは，公開画面，backendから受け取る公開データおよび自動検査を分離する．**

| 場所 | 役割 |
|---|---|
| `site/` | シミュレーター，詳細記事，共通表示およびホスティング処理 |
| `data/` | backendの公開成果物の受取，読込および版確認 |
| `qa/` | backend基準ケース，計算，HTML，リンクおよび統合の検査 |

Vite，Wrangler，Sitesおよびパッケージ管理がルートから設定を発見できるよう，`.openai/`，`vite.config.js`，`wrangler.jsonc`および`package.json`はルートに置くが，責任上は`site`の公開処理に属する．詳細は[site](site/README.md)，[data](data/README.md)および[qa](qa/README.md)を参照する．

## 人間とAIの役割分担

> **結論：AIが実装，データ反映および自動検査を担当し，人間は公開画面のUX，文章，情報の優先順位および見た目を判断する．**

通常，人間がJSON，テストfixtureおよび実装コードを直接編集する運用は想定しない．`data/input/`はbackendが生成した公開成果物を受け取り，`qa/`は自動検査とbackend基準計算との一致確認を担当する．人間は実ブラウザで公開画面を確認し，UX，文章，情報の優先順位および見た目に関する判断を[画面設計](site/docs/画面設計.md)へ反映する．

## ファイルの保持方針

> **結論：保持・清掃はAI分業を正本とし，frontend固有の資産と版別QA記録の扱いを補足する．**

共通の保持・清掃基準は[AI分業のファイル保持方針](../business-research/運営/AI分業.md#ファイルの保持方針)に従う．frontend固有の保持対象は，使用中の画像，受領した公開データと出典，QAの基準データ及び開発中の`node_modules/`とする．QAに記録した版別の検査実績は，現行の合格や作業指示と区別して保持する．

## 更新・確認手順

> **結論：開発コマンドは実装方針，検査範囲はQA，公開権限はAI分業を参照する．**

初回・依存関係更新時は`pnpm install`を実行する．日常の確認・ビルド手順は[ローカル開発](site/docs/実装方針.md#ローカル開発)，公開データの受領は[data](data/README.md)，検査範囲は[QA](qa/README.md#必須ケースと検査範囲)，公開処理は[site](site/README.md)を参照する．公開の承認・完了条件は[AI分業](../business-research/運営/AI分業.md#検収代理承認完了条件)に従う．`haretoku.jp`のDNSは公開内容の確認後に接続し，開発中の確認用公開では変更しない．

Git LFSを導入した環境でcloneし，既存の作業コピーでは検査前に`git lfs install`と`git lfs pull`を実行する．LFS対象は`qa/fixtures/calculation-cases.json`のみで，ポインタではなくJSON本体を取得してから検査する．Pagesのcheckoutも`lfs: true`で取得する．
